# OpenCode на втором ПК

Удалённое исполнение включается отдельно для каждого проекта: **Настройки →
«Запуск OpenCode на другом ПК по SSH» → Проверить изменения → Сохранить**.
По умолчанию оно выключено. У существующих проектов без `remote_execution`
сохраняется локальное исполнение.

Первый ПК запускает Codex, показывает UI и выполняет независимое ревью.
Второй Linux-ПК запускает совместимую сборку `agent-bridge`, OpenCode,
исполнителей и проверки. На каждом ПК свой Rust state и свои credentials.
MCP и OpenCode продолжают слушать loopback; SSH передаёт команды и ответы.
Пароли провайдеров второго ПК не копируются на первый.

## Подготовка

1. Установите одинаковую версию AIbridge на обоих ПК. На первом нужны Codex,
   Git и SSH; на втором — OpenCode, Git и инструменты проверок проекта.
2. Клонируйте один репозиторий GitHub/GitLab на оба ПК. Укажите локальный клон
   первого ПК как Workspace в UI. Клон второго зарегистрируйте в его
   `projects.toml` с **локальным режимом**, `execution_mode="worktree"` и
   `delivery_mode="manual"`. Настройте модели и API-ключи OpenCode на втором ПК.
3. Настройте SSH-доступ первого ПК ко второму через ключ/ssh-agent. Один раз
   подключитесь обычным SSH, проверьте адрес и сохраните host key. Мост использует
   `BatchMode=yes` и `StrictHostKeyChecking=yes`: интерактивный запрос пароля или
   принятие неизвестного ключа внутри фонового запуска не поддерживается.
4. Настройте неинтерактивный Git fetch/push **на обоих ПК** через SSH-ключи или
   credential helper. В URL проекта не вставляйте токены или пароли. Git-сервер
   должен разрешать создание веток `aibridge/*`.
5. В UI первого ПК включите настройку и заполните адрес, SSH-пользователя/порт,
   абсолютный путь к бинарнику, пути к конфигурации и Rust state второго ПК,
   ID проекта второго ПК и URL общего Git-репозитория. Пути относятся ко второму
   ПК и не проверяются как локальные каталоги первого.
6. Через кнопки Setup/Start/Doctor проверьте удалённый проект. В worktree-режиме
   исполнители запускают свои серверы задач по необходимости; глобальный Start
   требует MCP endpoint, как и в локальном режиме.

Пример привязки **первого** ПК:

```toml
[projects.demo]
workspace = "/home/user/projects/demo"
opencode_url = "http://127.0.0.1:4101"
password_file = "secrets/demo.password"
max_rounds = 3

[projects.demo.remote_execution]
host = "192.168.1.22"
user = "executor"
port = 22
executable = "/opt/aibridge/agent-bridge"
config = "/home/executor/.config/aibridge/projects.toml"
state_root = "/home/executor/.local/state/aibridge"
project = "demo"
repository = "git@gitlab.example:team/demo.git"
```

Порты в регистрации первого ПК сохраняются для совместимости локальной
конфигурации. Включённый удалённый режим использует адреса сервисов из
конфигурации второго ПК. Смена моделей/ключей в локальных полях не меняет
конфигурацию второго ПК.

## Автоматический пул задач

Согласуйте и утвердите JSON-план на первом ПК во вкладке «Автоматизация».
Перед стартом основной клон первого ПК должен быть чистым. Мост публикует
его исходный SHA через служебную Git-ветку. Второй ПК получает этот SHA и при
необходимости переключает свой чистый основной клон в detached HEAD на него.
Грязный клон, посторонний/неподдерживаемый checkout, активные задачи или другой
незавершённый запуск не перезаписываются.

Координатор второго ПК сохраняет задания и запускает OpenCode. Перед подготовкой
задачи и каждым ревью он публикует Git-коммит снимка в
`refs/heads/aibridge/<run UUID>/<tree SHA>`. Снимок создаётся через отдельный
индекс: HEAD и индекс рабочего checkout исполнителя не меняются.
Первый ПК получает ветку, проверяет SHA коммита и родителя и создаёт отдельный
checkout ревью в своём Rust state. Codex проверяет код там, отправляет приёмку,
замечания для следующего раунда или блокировку. Согласованные шаги, области
изменений и команды проверок сверяются при обмене.

При `delivery="manual"` итог остаётся в служебной Git-ветке; SHA и ref показаны
в UI. Получите её обычным `git fetch` и примените результат своим Git-процессом.
При `delivery="apply"` итоговые файлы переносятся в основной клон **первого** ПК
после итогового ревью. Доставка сохраняет журнал и допускает повторный запуск
после частичного применения. Изменение HEAD/индекса, конфликт файлов или
посторонние изменения блокируют перенос. Остановка не откатывает уже применённые
файлы; журнал и Git-снимок сохраняются. В основной ветке автоматических
commit/push нет. Основной клон второго ПК сохраняет исходный код запуска.

Пауза, продолжение и остановка адресуются тому же UUID на втором ПК.
Повтор admission после обрыва SSH находит существующий запуск, а не создаёт
новый пул. При недоступной сети первый ПК сохраняет блокировку; второй доходит
до ожидания ответа/таймаута или уже полученного control. Восстановите связь и
нажмите «Продолжить». Доставленная пауза/остановка прерывает ожидание модели;
невозможно доставить новый control при отсутствии соединения.

## Интерактивный Codex

«Codex через мост» остаётся на первом ПК и подключает stdio MCP через SSH.
Задачи и их история находятся на втором ПК. Для `task_status(task_id=...)`
в состоянии `awaiting_review`/`accepted` мост публикует снимок и возвращает
`review_workspace` на первом ПК, Git SHA, раунд и fingerprint. Codex должен
сначала проверить этот checkout. `accept_task` без такого снимка либо после
изменения задачи отклоняется. В интерактивном режиме исходный коммит двух
основных клонов синхронизируйте перед делегированием обычным Git; автоматическая
синхронизация исходного SHA относится к утверждённому автоматическому плану.

Dashboard и карточки задач читают удалённое состояние. Console и подключение
к OpenCode открываются через SSH PTY на втором ПК. Наборы связанных проектов
настраиваются на исполнителе; удалённые dashboard-запросы используют его реестр.
Редактор локального `opencode.json` и Git-веток по-прежнему относится к локальному
клону; конфигурацию OpenCode второго ПК меняйте на втором ПК.

## Проверка реализации

Интеграционный тест `agent-bridge-cli/tests/remote.rs` использует два независимых
клона/state root и bare Git-сервер. SSH и модели заменены протокольными fixtures;
production CLI, admission, координатор, workers, проверки, приёмка и доставка
работают полностью. Проверяются обновление исходного коммита, обрыв/продолжение,
доработка после ревью, отсутствие дублированных задач и сохранение HEAD/индекса
первого клона. Реальные LAN-доступ, ключи, GitHub/GitLab и провайдеры требуют
проверки в пользовательском окружении.

Git plumbing: [commit-tree](https://git-scm.com/docs/git-commit-tree),
[fetch](https://git-scm.com/docs/git-fetch).

Проверки изменения: конфигурация, runtime, automation и desktop проходят
последовательный набор тестов; удалённый workflow и настоящий Tauri WebView
проверены отдельно. В старом CLI-наборе `services` остаются два падения,
воспроизведённые на неизменённом HEAD: тест чужого непустого state directory
(`setup_refuses_symlink_credentials_and_foreign_state_without_writes`) и тест,
ожидающий `recoverable` в dashboard summary вместо detail
(`desktop_recovers_manual_continuation_after_401_runs_verifier_without_resending`).
